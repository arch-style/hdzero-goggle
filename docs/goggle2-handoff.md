## 分かっている事実 (改善策を考える材料)

- **I2C 1 番 (HDMI 出力、電池電圧、傾きセンサー、温度) は、電源から約 9 秒より
  前に触ると固まる。** 映像はこれを待たない作りにしてある (アプリの後回し)。
- **CPU のクロック:** ondemand は負荷を 2 秒に 1 回しか見ない。起動の多くは
  816 MHz で始まる。rcS の写しの先頭で最低クロックを最高に固定し、15 秒後に戻す。
  rcS より前 (preinit) の揺れ 0.3 s は残る。
- **画面の切り替え:** disp.ko の 1 秒の待ちを 100 ms にした写しを、カードから読む。
- **OSD のフォント:** アプリはカードの `resource/OSD/FC/` を先に探す。純正の
  BTFL のフォントを置くと、待ちが消える。
- **カード:** FAT の大きさがマウントの時間を決める (64KB クラスタで 0.12 s)。
  ファイルの数が増えると、純正の SD 状態ログの処理が 2 乗で遅くなる。
- **測る道具:** `app-sampler.sh` が動いていると、測定が乱れる (`.off` にする)。
- **ブートローダとカーネル:**
  - u-boot の環境変数は fw_printenv / fw_setenv で読み書きできる。
    initcall_debug の変更 (測るだけ) は 2 回とも無事だった。
  - u-boot の中の文字列からは、fatload、mmc、mw、bootm と、hush の if/then が
    入っていると読める。どう動くかは確かめていない (2026-10-19 の失敗はここ)。
  - カーネルの設定ファイル (/proc/config.gz) と pstore は無い。
  - ドライバの版の確かめ方は vermagic の文字列だけ (modversions 無し)。
- **作り直したカーネル:** 公開の lindenis-v536 の sun8iw16p1smp_defconfig に
  足し引きした設定 (config-hdzlike4) で、#69 と組み込みの関数の 99.4 % が一致する。
  展開後の大きさの差 (約 41 万バイト) は CONFIG_KALLSYMS_ALL だった (2026-10-20)。
  外した config-hdzlike5 は #69 との差 48,432 バイト。
  **一度も起動していない。**
- **SSH の reboot は戻らない。** 起動し直しは必ず電源ボタン。

## 失敗と教訓 (詳しくはメモリの feedback-verify-before-asserting.md)

- **2026-10-19:** u-boot の bootcmd を「カードのカーネルを先に試す」形に
  書き換えたら、次の起動からロゴで止まった。カードを抜いても止まった。
  - **原因:** u-boot の振る舞い (失敗した命令の後も続くか、失敗した bootm が
    無害か) を確かめないまま書いた。UART が無いので、確かめられていない。
  - **2026-10-20 の調べ (推測、根拠つき):** SDK の u-boot は起動のたびに bootcmd を
    128 バイトの配列へ strcpy する (board_common.c の update_bootcmd)。書いた bootcmd は
    181 文字で 54 バイトはみ出す。カードの有無に関わらず止まったことと合う。純正の
    u-boot にもこの関数の文字列がある。hush は失敗した命令の後も続ける (cli_hush.c)。
    **bootcmd は 127 バイト以内。** 詳しくは `docs/goggle2-card-boot.md` の (7)。
  - **教訓:** UART か、壊れないと分かっている起動の経路がない限り、bootcmd など
    起動の経路の環境変数は変えない。
- **測ったつもりで測っていなかった失敗:** 起動ごとの記録が上書きされていたのに、
  何回も起動を頼んだ。
- **確かめずに次へ進んだ失敗:** md5 の比べが動いていないのに、同じ命令でカードを
  取り出した。確かめる命令と次の操作は分ける。

## 改善策の計画 (2026-10-20 に見直し。段階 0 は済み)

見直しで一次情報を読み直し、前の案から 2 つを取り下げた。

- 「アプリが dispw の完了を自分で待つ」案: 起動を止めているのはライブラリの写し
  (boot 154: dispw 完了 3.03、libcopy 完了 3.19、起動 3.22) なので、得は無い。
- 「受信チップのバスを 1.2 MHz に」案: 1.2 MHz は I2C の上限を超え、FPGA が
  ついて来ないと測られている (`src/driver/dm6302.c:2075-2081`)。800 kHz が規格内の最速。

読んで分かった事実 (純正 rootfs を `mtd2-rootfs.bin` から展開して確認):

- `/pseudo_init` が devtmpfs をマウントし、`/dev/by-name/*` を作る (行 332、336)。
  rcS より前なので、rcS の `mdev -s` は無くても機器ノードと by-name はある。
- `/etc/mdev.conf` の規則は mmcblk/sd に対して `/usr/bin/hotplug.sh` を呼ぶだけで、
  その中身は全部コメントアウト (`exit 0` のみ)。
- `/mnt/UDISK` を使うのは `update_goggle.sh` (OTA で setting.ini を退避) と、アプリの
  起動時の `settings.c:491` (`/mnt/UDISK/setting.ini` があれば戻す) だけ。
- S01app (`/etc/init.d/S01app:57-59`) は vfat が未マウントのときだけカードをマウントする。
  先にマウントしてあれば何もしない。
- boot 154 では `mmcblk0: p1` が 1.10 s、rcS 開始が 1.52 s。カードは rcS の時点で見えている (1 回の観測)。
- アプリ本体が直接必要とする共有ライブラリは 46 本で、カードの g2lib 全部に相当する
  (`llvm-objdump -p` の NEEDED)。写す量は減らせない。カードの読み出しは
  「high speed SDHC」(50 MHz) なので、速いカードに替えても上限は変わらない。
- アプリの I2C の関門は port ごとに `HDZ_I2C<n>_NOT_BEFORE` で指定できる (`src/driver/i2c.c:64-80`)。
  受信チップ (port 2) を 3.5 s uptime ごろから使って問題なかったのは boot 44、153、154 で確認済み。
  それより早い時刻は未検証。
