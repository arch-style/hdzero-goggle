Goggle 2 起動高速化ノート

電源を入れてから HDZero の映像が出るまでを、純正の約 22 秒から 5 秒台へ近づける取り組みの記録です。何をして、何が分かり、いまどこにいて、次に何ができるかをまとめています。別のチャットで作業を続けるための資料も兼ねています。

02 Overview全体像

ゴーグルの中では、電源を入れると次の順に処理が進みます。実験は、この流れの 2 か所 (OS の初期化スクリプトとアプリ領域の起動スクリプト) に「SD カードを見に行く入口」を足し、中身をカード上のスクリプトで差し替えて行っています。カードを抜けば純正どおりに動きます。

起動の流れと、足した 2 つの入口の位置。紫がカードから差し替えられる部分。

ハードウェアの見取り図

速度を決めているのは、SoC (Allwinner V536) とその周りの部品のつながり方です。特に I2C という配線が 3 系統あり、そのうち 1 番だけに「電源を入れてからしばらく触ってはいけない」という性質があると分かりました。

赤い線が I2C 1 番。ここにだけ、決まった時刻まで通信を待たせる「関門」を置いています。緑の 2 番と 3 番は早くから使えます。フラッシュの帯は各領域の大きさの比。

今 (段階 62、2026-10-17)。映像まで 6.37 秒。rcS の先頭から CPU を最高クロックに固定し、カードのマウントは 0.25 秒。映像は I2C 1 番の関門 (9.0 秒) を待たずに出て、1 番の部品は映像の後に裏で初期化する。

ブートローダ・カーネル OS の初期化 カードのスクリプト アプリ 待つだけ 映像が出た時刻

時計が 2 つあることに注意。 アプリのログの時刻は「電源を入れた瞬間から」、/proc/uptime やカードの rc-exp.log・init-exp.log は「カーネルが動き出した瞬間から」です。差はブートローダの時間で、約 1.40 秒。図はすべて電源からの秒に直しています。

04 Findings分かったこと

ハードウェア

I2C 1 番は、早く触ると固まる

カーネル起動から 4.3 秒や 6.2 秒で 1 番に触ると、以後すべての通信が時間切れになり、電源を切るまで戻りませんでした。7.6 秒なら問題ありません。2 番と 3 番は 6.5 秒からでも大丈夫でした。

準備ができたかを通信で確かめること自体が早すぎる通信になるので、決まった時刻まで待つ方式にしています (I2C_NOT_BEFORE=7.6)。

純正の作り

純正の sleep は、隠れた待ちだった

USB の準備の sleep 2 と rc.sh の sleep 1 は、意図せず I2C 1 番の準備を待つ役目をしていました。USB の準備の中身そのものは不要です (Goggle 2 には USB の口が無い)。

待ちを消すと固まり、待ちを「必要な所だけ」に置くと速くなる。

画面

rc.sh の画面設定 (dispw) は外せない

外すと fork は画面の初期化 (lvgl_init) で落ち、代わりに起動した純正も止まりました。ただし裏で並行して走らせたり、3.8 秒ごろに前倒ししたりするのは問題ありません。

アプリの画面の初期化より前に終わっていればよい。

読み込み

アプリと録画プロセスは同じライブラリを読む

共有ライブラリ 48 個、約 7.5MB。これに fork 本体 3MB を足した約 11MB を、待ち時間のうちに読んでおくと (先読み)、アプリの起動が 0.5〜0.7 秒速くなりました。内蔵フラッシュの読み出しは毎秒約 5MB。

一覧は preload.goggle2.txt。2 つが同時に読み込むと取り合って遅くなる。

測定

ブートローダは約 1.4 秒

アプリのログ (電源からの時計) とカーネルの記録 (カーネル起動からの時計) を、同じ画面設定の出来事で突き合わせて分かりました。前後とも 1.40 秒で一致。

2 つの時計を混ぜて引き算すると、ありもしない遅れが見えてしまう (一度これで分析を誤った)。

画面

画面切り替えの 1 秒は disp.ko の待ち

dispw で出力を切り替えるたびの 1.1 秒は、ドライバ disp.ko の disp_vdpo_disable() の最後にある disp_delay_ms(1000) でした。4 バイト書き換えて 100 ms にした写しをカードから読み込むと、dispw -s vdpo 720p60 が 1.11 秒から 0.19 秒になり、画面の乱れもありません。

disp.ko はアプリ領域 /mnt/app/ko から読まれるので、フラッシュに書かずに差し替えられる。作り方は goggle2-ko/README.md。

OS

udev は udevd だけ動かせばよい

一斉認識 (udevadm trigger と settle) を省き、udevd だけを裏で起動しても、SD の抜き差しのマウントは働きます。規則が作るリンクのうち使われているのは /dev/rtc だけで、これが無いと fork が時計の画面で落ちました。ln -s rtc0 /dev/rtc で足ります。

/dev の差分は by-id などのリンクだけで、ほかは誰も使っていない。fork 側も、時計が読めないときに落ちないよう直した。

読み込み

ライブラリはカードから写す方が速い

アプリと録画プロセスが使う共有ライブラリ 47 本 (7.1MB) と fork 本体 3.3MB を、カードがマウントされた直後に /tmp へ写すと、内蔵フラッシュ (毎秒約 5MB) からの先読みより速く、取り合いも起きません。LD_LIBRARY_PATH の先頭に /tmp/lib を置きます。

中身は純正の rootfs の写しで、md5 一覧は goggle2-ko/g2lib.md5。

受信チップ

efuse は控えておける

受信チップ (DM6302 ×2) の初期化は、毎回 efuse を読みます。チップのレジスタから作った鍵と一緒にカードの efuse-cache.bin (3124 バイト) に控え、次からは読み出しを省きます。控えから戻した値の指紋は、読み出した値と同じでした。

鍵が合わなければ読み直すので、別のゴーグルに挿しても誤った値は使わない。

カード

FAT の大きさがマウントの時間を決める

このゴーグルの vfat はマウント時に FAT 全体を読みます。64GB・32KB クラスタのカードは FAT が 7.8MB で 0.62 秒、32GB・64KB クラスタの HDZERO_BOOT は 1.9MB で 0.12 秒でした。マウント全体では 0.79 秒が 0.25 秒になります。

作り方は Mac で sudo newfs_msdos -F 32 -c 128。ディスクユーティリティではクラスタの大きさを選べない。

ばらつき

起動の揺れは CPU のクロックだった

ondemand は負荷を 2 秒に 1 回しか見ません (sampling_rate 2000000 µs、io_is_busy 0)。多くの回は 816 MHz のまま起動し、ときどき最初から 1104 MHz で走ります。どちらになるかで、カードより前の区間が 0.5 秒違いました。温度は 41 ℃ で、制限の 80 ℃ よりずっと下です。

rcS の写しの先頭で最低クロックを最高に固定し、15 秒後に戻す。残りの差 0.3 秒は rcS より前 (preinit) で、カーネルかブートローダでしか直せない。

失敗から

道具の消し忘れが測定を乱した

新しいカードを作るとき、前のカードで止めていた app-sampler.sh を有効なまま写しました。50 ms ごとにコマンドを起動し続けるので、受信チップとのやり取りが 2 倍に延び、映像が 0.4 秒遅れました。止めると元に戻りました。

作り直すときは、前の実物の中身と突き合わせる。check-sd.sh が有効な app-sampler.sh を NG にする。

通信

Wi-Fi は動く。ゴーグルが問い合わせに応えないだけ

ゴーグルの Wi-Fi は 2.4GHz 専用です。つながっていても、Mac からの「この IP は誰?」(ARP) にゴーグルが応えません。ゴーグルから Mac へ一度 ping を出せば、以後 SSH が通ります。コワーキングスペースの Wi-Fi は端末どうしの通信を遮るので、SSH は自宅でだけ使えます。

wifi-hello.sh が起動ごとに Mac へ ping を出す。自宅での IP は 192.168.40.229 か .246 で、ルーターの一覧には hdzero.lan と出る。

安全

ブートローダが壊れても戻せる

SD の緊急更新 (HDZG_OS.bin ほか) はカーネル・OS・アプリ領域まで書き直します。さらに PhoenixCard (公式の Method 4) でカードに書いた HDZG_OS.bin は boot0 から起動する復旧カードになり、2026-10-16 に実機で全体を戻せました。設定は初期化されるので、控えと書き戻しの仕組みを用意しています。

これがあるから、フラッシュの起動スクリプトに手を入れられた。ブートローダやカーネルの作り直しにも進める。

失敗から

SSH の reboot では戻らない

SSH から reboot を実行すると、画面が真っ暗でファンが回ったまま止まり、カードの記録も始まりませんでした。純正も再起動は使わず、更新の後は「電源を入れ直してください」と出すだけです。32MB の NOR が 4 バイトアドレスのまま残るなど、温かい再起動を想定していない作りと見ています (未確認)。

起動し直すときは、必ず電源ボタンで切って入れる。

失敗から

アプリ本体を「試しに」実行しない

ライブラリの読み込み時間を測ろうとして、glibc 用の指定でアプリを実行したら、musl では効かずアプリが 2 つ同時に動きました。止めて電源を入れ直し、実害はありませんでした。

読み込みだけ測るなら /lib/ld-musl-armhf.so.1 --list を使う。

測定

アプリは最後に使った入力で起動する

fork は setting.ini の last_source の入力で起動します。アナログで終えると、次の起動もアナログになり、HDZero の映像の時刻が取れません。HDZERO_BOOT の最初の 3 回がそうでした。Wi-Fi をオンにすると、アプリの開始から映像までが約 0.2 秒延びます。

測る前にメニューで HDZero に戻し、Wi-Fi のオンとオフをそろえて比べる。

カードに入れて試す

  1. ゴーグルが動いていれば SSH で /mnt/extsd/ に scp し、md5sum で一致を確かめる。カードが Mac にあれば直接コピー。
  2. 関門入りの本体を入れたら、本体に HDZ_I2C_NOT_BEFORE の文字列があることを確かめてから HDZGOGGLE.features に i2c_gate と書く。これが無いと rc-exp.sh はアプリを関門の後に起動する (関門の無い本体で早く起動すると I2C が固まるため)。
  3. Mac でカードを点検: utilities/sdcard-test/check-sd.sh /Volumes/HDZERO_BOOT が OK になること。
  4. ユーザーに電源ボタンでの入れ直しを頼む (reboot は使わない)。記録を書き終えると 2 ms のビープが 1 回鳴る (起動時には鳴らさない)。
  5. SSH かカードで rc-exp.log・init-exp.log・boot-logs/boot<N>-stage<S>.log を読む。カードより前の区間と CPU のクロックの履歴は boot-logs/early-stage<S>.txt (dmesg の bootmark: の行)。

時刻の読み方

  • rc-exp.log・init-exp.log はカーネル起動からの秒。電源からにするには +1.4。
  • HDZGOGGLE.log は最初 1970 年の時刻 (電源からの秒)、途中から 2026 年の仮の時計。最後の 1970 行と最初の 2026 行を同じ瞬間とみなしてつなぐ。
  • HDZero の映像は boot: picture at Nms (main からの ms) か、switch to bw の後の OLED: Display on。
  • 関門の動きは i2c: port N not before … と i2c: port N opened at …。I2C のエラーは i2c: port N, addr … took。

次にすること: カード側の小さな詰め (ライブラリの写し待ち、OSD の組み立て) を、電源ボタンで数回ずつ起動して測る。Wi-Fi は SSH に要るのでオンのまま比べる。普段の入力は HDZero が多く、次がアナログ、AV はあまり使わない。公共の Wi-Fi では Mac から特別なこと (固定 IP、掃引など) をしない。

08 Next次の高速化

映像は I2C 1 番の関門を待たず、起動中の CPU は rcS の先頭から最高クロックです。いまの 6.37 秒は、ブートローダとカーネルで 2.6 秒、rcS より前の preinit で 0.7 秒、rcS とカードのマウントまでで 1.0 秒、カードのスクリプトで 0.7 秒、アプリで 1.4 秒です。

今の 6.37 秒の内訳 (段階 62、起動時のクロックが 816 MHz だった回)。1104 MHz で始まる回は preinit が 0.3 秒短く、6.06〜6.14 秒。

09 Terms用語

I2C部品どうしをつなぐ 2 本線の通信。ゴーグルには 1〜3 番の 3 系統
関門 (I2C_NOT_BEFORE)カーネル起動から決まった秒数になるまで I2C 1 番の通信を待たせる仕組み。アプリ側は環境変数 HDZ_I2C1_NOT_BEFORE、カード側は rc-exp.sh
dispwSoC の映像出力 (VDPO) の設定を変えるコマンド。純正の disp.ko では 1 回約 1.1 秒、差し替えた disp.ko で約 0.2 秒
udev / udevdデバイスを認識して /dev を整える仕組み。udevd は常駐して SD の抜き差しを扱い、起動時の一斉認識 (trigger、settle) は省ける
段階 (stage)カードの stage.txt の番号。init-exp.sh が起動ごとに 1 つ進め、番号で実験の設定を選ぶ
直接起動 (FAST_LAUNCH)rc-exp.sh が develop.sh の連鎖を通さず、/tmp に写した fork を起動すること
efuse受信チップに工場で焼かれた調整値。初期化のたびに読んでいたものをカードに控える
PhoenixCardAllwinner の Windows ツール。HDZG_OS.bin を書いたカードは boot0 から起動して全体を書き直す復旧カードになる
上書き領域 (overlay)書き換えできない OS 本体の上に、変更分だけを置く 512KB の領域
先読み (preload)後で使うファイルを先に読み、メモリに置いておくこと。段階 9 からは、カードから /tmp への写しに置き換えた
ondemandCPU のクロックを負荷に合わせて変える仕組み。このゴーグルでは負荷を 2 秒に 1 回だけ見る
bootmarkrcS と rc.final が /dev/kmsg に書く区切りの印。dmesg にカーネルの時刻付きで残る
クラスタFAT32 がファイルに割り当てる単位。大きいほど FAT が小さくなり、マウントが速い
緊急更新SD に復旧用ファイルを置いて電源を入れると、ブートローダがフラッシュを書き直す仕組み
